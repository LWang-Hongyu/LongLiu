## 二、实现方案（已废弃 — 被 DSCP 方案取代）

> ⚠️ 本节内容对应 nccl-master/proxy quota 方案，已于 2026-06-29 被 **nccl-dscp DSCP 方案** 取代。
> 保留仅作参考，不再继续开发。

### 2.1 架构总览（已废弃）

PyTorch DDP Training Process
  |
  +-- Python Hook (job_a.py / job_b.py 内联)
  |   -> ctypes.CDLL(libnccl.so.2) 加载 LongLiu 符号
  |   -> 每轮迭代调用 ncclLongLiuIterStart() / End()
  |   -> NCCL proxy thread 内部计算 deficit -> 调整 quota
  |
  +-- NCCL Proxy Thread (ncclProxyProgress)
      -> 每轮循环读 priorityLevel 状态
      -> quota = map_priority_to_quota(priorityLevel)
      -> 控制本轮处理的 ops 数量
      -> pi > 0 -> priority up -> quota up -> 占更多带宽
      -> pi < 0 -> priority down -> quota down -> 让出带宽

### 2.2 LongLiu 核心逻辑（已废弃）

进度赤字 (Progress Deficit):
  pi_i = A_i(t) / (c_i x T_target x k_i(t)) - 1

其中:
- A_i(t): 累积通信时间
- k_i(t): 已完成的迭代数
- T_target: 目标迭代时间（自测量）
- c_i: 松弛系数（>1，用户提供的SLA等级）

优先级映射:
  pi > 0.3  -> P6 严重违约 -> 最高配额
  -0.1 < pi <= 0.3 -> P4 轻度违约 -> 高配额
  -0.5 < pi <= -0.1 -> P2 正常 -> 默认配额
  pi <= -0.5 -> P0 超前 -> 最低配额

## 三、当前方案：nccl-dscp DSCP 带宽控制

### 3.1 方案概述

通过修改 NCCL 源码，在通信初始化时为每个 IB QP 设置不同的 DSCP（Differentiated Services Code Point）值，利用 RoCEv2 网络的 QoS 机制实现带宽优先级控制。

### 3.2 源码结构

| 文件 | 作用 | 状态 |
|------|------|------|
| src/misc/dscp_adapter.cc | DSCP 适配器核心逻辑：epoch tracking、priority 计算、DSCP 映射 | ✅ 已实现 |
| src/include/dscp_adapter.h | DSCP 适配器数据结构定义 | ✅ 已实现 |
| src/transport/net_ib.cc | `ibv_modify_qp(IBV_QP_AV)` 修改 QP traffic_class | ✅ 已修改 |
| src/enqueue.cc | epoch 集成（StartEpoch/EndEpoch 调用点） | ✅ 已修改 |
| src/init.cc | 初始化时启动 DSCP adapter | ✅ 已修改 |
| src/misc/comm_stats.cc | 通信统计（被 dscp_adapter 引用） | ✅ 已修改 |
| src/misc/socket.cc | socket DSCP 设置（setsockopt IP_TOS） | ✅ 已修改 |

### 3.3 实现原理

1. **Epoch tracking**: 将训练过程划分为 epoch，每个 epoch 内统计通信字节、持续时间等
2. **Urgency Index 计算**: `UI = A_i(t) / (SLO × E_i(t))`，其中 A_i 是实际累积时间，E_i 是期望时间
3. **DSCP 映射**: UI 值映射到 7 级 DSCP 码点（0, 18, 28, 26, 36, 34, 38），对应不同优先级
4. **QP 更新**: 通过 `ibv_modify_qp(qp, &attr, IBV_QP_AV)` 动态修改 QP 的 traffic_class

### 3.4 编译与部署

- 源码目录: `nccl-dscp/` (基于 NCCL 2.18.3)
- 编译: `cd nccl-dscp && make -j src.build BUILDDIR=./build`
- 部署: `cp build/lib/libnccl.so.2.* <pytorch-nccl-path>`
- 当前状态: 宿主机 rdma-core 版本（58mlnx43）与 NCCL 2.18.3 不兼容，编译失败
- 备注: 容器内编译产出可通过 rsync 从 226 同步

### 3.5 连通性验证

通过 test_dscp_qp.c（链接 libibverbs）验证：
- `ibv_query_qp(IBV_QP_AV)` — 驱动支持查询 AV 属性 ✅
- `ah_attr.grh.traffic_class` — 结构体字段可用 ✅
- `ibv_modify_qp(IBV_QP_AV)` — 需在 INIT→RTR 状态转换时调用 ✅
- rdma-core 58mlnx43 完全支持 DSCP 所需的 verbs API

## 四、Multi-Job 竞争实验方案（proxy quota 方案）

由于只有2节点2卡（226有2GPU，10.1有1GPU），竞争实验设计:

节点分配:
  226 (2 GPU): Job A master on GPU0, Job B master on GPU1
  10.1 (1 GPU + MPS): Job A worker + Job B worker on GPU0 (MPS共享)

启动顺序（MPS限制, 两个独立NCCL communicator无法同时初始化）:
  1. 启动 Job A worker + master
  2. 等待 Job A 完成 (~30秒)
  3. 启动 Job B worker + master
  4. 等待 Job B 完成 (~60秒)

## 六、RDMA 原型验证（proxy quota 方案）

> ⚠️ 本节对应已废弃 proxy quota 方案的前期调研，仅供参考。

### 6.1 ibv_modify_qp() 动态 TC 修改

结论: 通过标准 ibverbs API 修改 traffic_class 需要 INIT→RTR 转换时设置，不适合运行时动态调整。

### 6.2 LD_PRELOAD 拦截 ibv_post_send

结论: 不可行。ibv_post_send 是 static inline 函数，LD_PRELOAD 无法拦截。

### 6.3 NCCL proxy quota 方案（已废弃）

通过在 NCCL proxy thread 中修改 ops quota 实现带宽控制，已被 DSCP 方案取代。
